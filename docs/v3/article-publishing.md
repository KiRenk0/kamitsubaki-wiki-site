# 独立文章系统：投稿、数据库与后台审核

更新于 2026-09-20。本说明替代原先“文章通过百科编辑器和 GitHub PR 发布”的方案。

## 入口与职责

- `/zh/articles/`：从文章 API 读取已公开文章，支持搜索、分类、分批加载。
- `/zh/articles/submit/`：登录后保存数据库草稿、继续编辑、提交审核；阅读页的“提交修改”会载入当前公开版本。
- `/zh/articles/read/?id=文章ID`：独立文章阅读器，复用站内 Reader，提供正文目录和关联词条。
- 后端 `/admin/articles`：管理员查看待审全文及当前公开版本、填写审核意见、批准或退回、下架与恢复公开文章。
- 旧 `/articles/分类/ID/` 链接转向数据库阅读页。旧百科编辑入口的 articles 参数转向独立投稿页；GitHub 投稿接口拒绝新文章草稿和提交。

百科 Markdown 与文章数据库各自维护。文章发布不创建 GitHub PR，也不需要重建静态站。账号沿用现有登录体系，不创建第二套账号。

## 投稿流程

1. 填写标题、语言、分类和正文；摘要与关联词条 ID 可选。
2. 保存草稿后内容存入 D1，可从“我的文章提案”继续编辑。草稿允许内容未填完，提交必须有标题与正文。
3. 正文使用 Markdown，提供标题、粗体、链接、图片网址工具及安全预览。当前图片通过网址插入，文章页尚不提供独立文件上传控件。
4. 提交后进入待审，公开文章继续显示此前批准版本。退回意见可在个人提案中查看，并复制修改后重新投稿。
5. 管理员批准后公开。任何登录用户均可对公开文章提出修改，但不能直接覆盖文章或审核自己的权限之外的提案。

文章列表每批 24 篇，个人提案与后台队列每页 20 项；关联档案首屏最多展示 12 篇，提供完整关联文章列表入口。

## 数据结构与一致性

迁移文件：后端 `migrations/0021_articles.sql`，使用现有 `AI_OBSERVER_DB` D1 绑定，建立独立文章表，不复用百科投稿表。

- `article_documents`：稳定 ID + 语言作为主键，存公开正文快照、公开状态、版本号与批准修订 ID。
- `article_revisions`：每次提案的作者、基准版本、正文、draft/pending/approved/rejected 状态和审核记录。
- `article_audit`：下架及恢复记录。
- `article_import_sources`：旧 Markdown 的完整原文、原路径和 SHA-256，保留 frontmatter，便于核对和追溯。

批准时以版本号和修订 ID 作条件更新，通过 D1 batch 一并记录公开版本和批准结果。同一旧版本的第二份提案会提示冲突，不能静默覆盖；下架和恢复也增加版本号。服务器限制正文 200,000 字符、关联 ID 50 个、每天每人新建 30 份提案。浏览器写操作检查 Origin，审核接口检查管理员身份。公开接口不返回草稿。

关联词条使用稳定 ID。词条阅读器展开文章区时查询 D1，因此新增文章不依赖静态百科关联索引刷新。文章中的关联词条通过现有 catalog-index 解析到实际路径。

## 部署与旧内容迁移

1. 备份 D1，先在预览环境应用 `0021_articles.sql`，部署匹配的 Worker。
2. 在主站运行 `node scripts/v3/export-article-import.mjs /tmp/article-import.sql`。脚本只读取 `src/content/articles`，输出 SQL 与逐文件哈希报告，不修改原文、不操作远端。
3. 将 SQL 应用到目标预览数据库。导入按源文件哈希幂等；原文存档和待审提案同时保留，导入不会覆盖公开文章。
4. 后台逐条检查并批准需要继续公开的历史文章。**旧链接转向数据库之前，必须完成历史文章导入及批准，避免旧链接无公开内容。** 不要删除源文件存档。
5. 配置 `PUBLIC_ARTICLE_API_URL` 为对应 Worker 地址。开发环境暂可回退到 `PUBLIC_GALLERY_API_URL`，默认生产 API 为 `https://api.kamitsubaki.wiki`。检查该前端 Origin 在 Worker 白名单中。
6. 验证真实登录、投稿、审核、修改、旧链接与下架恢复后，再发布匹配前端。

本轮不执行远端迁移或部署。本地内存数据库验收不代表云端服务已启用。阅读正文目前由浏览器从 API 加载，静态 HTML 不包含正文，完整搜索引擎预渲染不属于本轮实现。

## 维护与检查

后端 `src/articles/manager.js` 是投稿/审核共享界面的源文件；主站执行 `node scripts/v3/sync-article-manager.mjs` 同步，`--check` 验证镜像一致。页面框架使用 WorkspaceLayout，阅读器使用 Reader。

后端检查：`node --test tests/articles.test.mjs`。主站检查：`pnpm exec astro check`。改动涉及数据库事务或审核权限时，应覆盖草稿隐私、普通用户不能审核、重复审批与基准版本冲突。真实发布验收仍必须用实际账号和 D1。
