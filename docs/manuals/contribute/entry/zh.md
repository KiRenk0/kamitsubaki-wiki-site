## 进入正确的词条

修改现有词条时，先打开该词条的当前语言页面，再用阅读器的编辑入口；编辑器会带入对应源文件。新建时从[贡献中心](/zh/contribute/)打开[词条编辑器](/zh/contribute/editor/)，在顶部“文件”菜单选择新建词条，指定实体类型与源语言。简中、日文、英文是维护源；台湾与香港繁体由简中生成，不直接创建繁体源稿。

阅读器中的“完善此词条”、待补全提示和完善度缺项也会打开同一词条的编辑器；它们不是不同的投稿渠道。[百科目录](/zh/database/)的“新建词条”进入编辑器的新建流程。筛选无结果不代表词条不存在，请先清除条件、搜索别名，避免重复创建。

## 填写内容与属性

正式写作前，请同时打开[内容与格式完整指南](/zh/docs/contribute/format/)：它保留原有的结构、命名、文风、来源、时间、媒体、隐私和多语言规范，以及各类词条骨架和提交前清单。Markdown、frontmatter、媒体短语法与字段实例则在[语法与属性完整指南](/zh/docs/contribute/syntax/)；这两份是完整参考，不是本章的简写替代品。

先搜索别名，避免重复实体。新词条的稳定 ID 使用小写英文、数字及连字符，跨语言保持一致；显示名称可翻译，ID 不随改名变化。按类型完成编辑器标明的必填属性，再写正文。封面、关系、表演者、制作署名等字段在“词条属性”填写；不要把网页 URL 当成仓库文件路径。占位词条也应写明已确认资料与来源，不用猜测填满字段。

编辑区与预览可并排查看；用大纲检查章节、目录和锚点。插入内容可从按钮或 `/` 菜单选择，源码模式用于保留扩展语法。修改旧词条时不要为了排版删除原有事实、引用或未知语法；提交前查看差异，核对图片、关联和资料来源。

## 图片与附件

词条附件属于 **GitHub PR 链路**，不是设定图库。编辑器可选取、拖入或粘贴 PNG/JPEG/WebP 原图，并要求填写来源；附件先保存在当前浏览器，提交时与正文进入同一个 PR。当前站内限制为**单张 750 KB、最多 8 张、合计 4 MB**，不会自动压缩。超过限制的原图须按 GitHub 仓库投稿流程上传，并在同一 PR 中引用；填写图片网址不会自动上传文件。仓库 `public/images/...` 对应网页地址 `/images/...`，不能填本机路径或 `/public/images/...`。

## 检查、提交与继续

检查必填项、事实来源、正文预览、关联、语言及修改说明。登录且投稿服务可用时，点击顶部**提交 GitHub PR**；提交回执给出记录入口。若按钮显示投稿暂不可用，先保存或导出草稿，勿把本机保存理解为已投稿。提案审核、GitHub 合并和站点部署完成后，修改才出现在公开词条；退回意见与继续编辑见[审核说明](/zh/docs/contribute/review/)。

## 元数据决定哪些页面出现内容

旧贡献指南的字段表仍适用于 V3。`schemaVersion: 2` 是**元数据协议**，不是网站 V3 版本号。先在编辑器选择实体类型，再按实际字段填写；不要把所有关系仅写在正文里。

| 字段 | 页面用途 | 投稿时检查 |
| --- | --- | --- |
| `id`、`locale`、`entityType` | 跨语言身份、内容类型与规范地址 | 同一实体的三种源语言沿用同一 ID；不要重用别的实体 ID。 |
| `name` 或 `title` | 标题与目录名 | 使用可靠的官方名称；译名与原名可分别标注。 |
| `presentation.image`、`presentation.theme` | 封面、阅读器背景与局部主题色 | 图片地址能直接打开，颜色不替代正文证据。 |
| `presentation.morphing` | 图片＋名字的形态切换 | 仅用于同一谱系中真实存在的独立档案。 |
| `classification.primary`、`classification.additional` | 主归档及额外分类入口 | 主分类决定规范位置；额外分类不能复制正文。 |
| `relations`、`performers`、`credits` | 关联档案、作品署名与反向链接 | 填稳定实体 ID，并确认关系类型。 |
| `sources`、`license` | 可核对来源及文字许可 | 许可不能替代媒体使用依据。 |
| `contentStatus`、`lifecycle` | 占位／正式内容与活动状态 | 不确定的日期留空；占位不等于猜测填满。 |

分类以[详细分类地图](/zh/docs/develop/content/)及当前目录配置为准。一个词条可以出现在多个分类入口，但只有一份各语言正文和一个规范地址。新团体成员需要团体实体及真实的 `member-of` 关系；不要因为人物也在个人活动，就自动把团体成员放入个人层级。歌曲演唱者用 `performers`，作品制作署名用 `credits`，团体所属用对应关系。修改主归档或旧路径会涉及重定向，应交由维护者检查，不能只移动文件。

## 大于站内附件限制的原图

下面是旧图片指南中仍有效的 GitHub 流程，**只适用于词条附件**；图库始终走图库上传器。原图保留原始字节、分辨率和格式，无须为了投稿强制转成 WebP。

1. 在网站仓库建立本次投稿分支；没有写入权限时先 Fork。确认目标是维护者指定的开发分支，不直接写发布分支。
2. 将原图放入 `public/images/` 下合适目录，以小写英文文件名标识内容；确认大小写和扩展名。GitHub 网页上传单文件上限为 25 MiB，仓库静态资源审计也有限制，更大的文件先与维护者核对。
3. 在**同一分支和 PR** 修改相应 Markdown，填写来源、作者及使用依据。仓库地址 `public/images/example.jpg` 对应页面地址 `/images/example.jpg`。不要填 `/public/images/...`、本机路径、临时 `blob:` 网址或 GitHub 的文件浏览页面地址。
4. 在 PR 的 Files changed 核对图片和 Markdown 都已进入提案。合并、部署后再访问实际图片地址与词条；上传成功本身不会更新页面。

若图片先前已部署，可直接在编辑器引用其 `/images/...` 地址；若图片与新词条同批提交，线上预览在部署前可能显示断图。替换图片优先使用新文件名，并搜索封面、正文和其他语言引用，避免旧图缓存或断链。站点缩略图不会覆盖仓库原图。

## 提交前逐项核对

- 该实体是否已经存在别名或其他语言版本；主分类是否与详细地图一致。
- 事实、日期、引文和图片是否有可追溯来源；没有证据的内容是否明确标为待核实。
- 原正文中的正确内容、未知扩展语法及来源是否保留；差异是否只包含本次有意修改。
- 正文目录、锚点、图片地址、关联 ID 和多语言身份是否在预览中正确。
- 回执是否提供记录编号；没有回执时先查创作者中心，不重复创建相同 PR。
