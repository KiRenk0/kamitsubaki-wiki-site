## 仓库职责

`kamitsubaki-wiki-site` 是 Astro 前台与百科 Markdown 的来源，`kamitsubaki-wiki-site-backend` 提供登录、投稿、审核及接口。工作区根目录 `docs/` 是主站仓库 `docs/` 的镜像；只修改主站来源，再运行 `node scripts/sync-docs.mjs`。不要把镜像或构建产物作为正文来源。

## 三条数据链路

百科词条从 Markdown 和元数据构建静态页面；站内编辑器把修改作为 GitHub PR 提案，审核合并并发布后才更新网页。文章保存在 D1 的独立文稿与修订表，批准后通过公开 API 阅读；不创建百科 PR。图库由 Worker 接收图片，先进入私有 R2 暂存，集合和逐图修订保存在 D1；批准后才进入公开读取路径。创作者中心通过适配层汇总三类记录，不把三种存储或状态强行混为一种。

## 权限与公开边界

公共读取只返回已公开版本。登录用户可保存和提交自己的草稿，也可对公开内容提出修改；审核接口核对维护者身份、版本及归属。图库上传成功、词条 PR 合并、文章审核通过分别有不同的最终公开条件。前端的状态文案必须表达实际服务状态，不凭按钮点击推测成功。

## 请求与公开路径

| 内容 | 投稿入口与暂存 | 审核后如何给公众读取 | 更新是否依赖前端构建 |
| --- | --- | --- | --- |
| 百科词条 | 前端编辑器 → Worker 投稿服务 → GitHub PR | 合并到源仓库并发布静态页面 | 是 |
| 文章 | 共享编辑器 → D1 草稿和修订 | 批准修订由文章公开 API 提供 | 否 |
| 设定图 | 上传工作台 → Worker → 私有 R2 暂存、D1 记录 | 集合与图片获批后由公开接口和图片域名提供 | 否 |

接口读取当前用户记录时要检查身份和归属；公开 API 不能返回草稿或未审核文件地址。图库公开对象与暂存对象分开，图片传输 100% 只表示客户端数据发送结束。审核端必须验证版本和权限，避免两个维护者对同一旧版本的操作互相覆盖。

## 目录与镜像边界

主站 `docs/manuals/` 是三本说明书唯一正文来源，工作区外层 `docs/` 只作镜像。`src/content/` 保管百科原稿，`src/data/` 保管分类和时间轴等结构化数据；文章正文和图库修订在数据库，不要以新的 Markdown 文件假冒其公开状态。部署前记录主站和 Worker 的匹配提交，以及 D1 迁移与 R2 binding；前端页面能构建并不证明线上写入已联调。
